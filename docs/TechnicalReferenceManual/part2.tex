\section{API 상세 명세}
\label{sec:api_detail}

\pymodule{} 모듈의 \texttt{api.py}는 시뮬레이션 엔진의 핵심 기능을 수행하는 4개의 주요 함수를 제공한다.

% ---------------------------------------------------------------------------- %

% ---------------------------------------------------------------------------- %
\subsection{시뮬레이션 실행 함수}

\begin{codebox}{run\_grjson / run\_grexcel}
\small
\textbf{Definition:}
\begin{verbatim}
def run_grjson(input_filepath, output_filepath=None, *, save=True) -> str | dict
def run_grexcel(input_filepath, output_filepath=None, *, save=True) -> str
\end{verbatim}
\end{codebox}

\noindent 두 함수는 각각 JSON(.grm)과 Excel(.xlsx) 포맷의 모델을 입력받아 시뮬레이션을 수행한다.

\begin{table}[htbp]
    \centering\small
    \begin{tabularx}{\textwidth}{l l X}
    \toprule
    \textbf{매개변수 (Args)} & \textbf{타입} & \textbf{설명} \\
    \midrule
    \texttt{input\_filepath} & \texttt{str} & 입력 파일 경로 (확장자 생략 가능) \\
    \texttt{output\_filepath} & \texttt{str | None} & 결과 저장 경로. \texttt{None}일 경우 입력 파일명에 \texttt{\_out} 접미사를 붙여 자동 생성 \\
    \texttt{save} & \texttt{bool} & \texttt{True}일 경우 결과를 파일(.grr)로 저장, \texttt{False}일 경우 딕셔너리로 반환 (\texttt{grjson} 전용) \\
    \bottomrule
    \end{tabularx}
\end{table}

def get_database(datatype, key, *, as_dict=False) -> object | dict

    \textbf{매개변수} & \textbf{타입} & \textbf{설명} \\
    \midrule
    \texttt{datatype} & \texttt{Literal} & 조회 대상 DB 종류 (\texttt{material}, \texttt{schedule}, \texttt{surface\_construction} 등) \\
    \texttt{key} & \texttt{str} & 아이템 식별자. 복합 구조체(Construction)의 경우 속성을 \texttt{\&} 기호로 연결하여 문자열로 전달 \\
    \texttt{as\_dict} & \texttt{bool} & \texttt{True} 설정 시 객체가 아닌 딕셔너리(JSON 호환 포맷) 형태로 반환 \\
    \bottomrule
    \end{tabularx}
\end{table}

\subsection{포맷 변환 함수}

\begin{codebox}{convert}
\small
\textbf{Definition:}
\begin{verbatim}
def convert(input_filepath, src, dst, *, output_filepath=None) -> None
\end{verbatim}
\end{codebox}

\noindent 입력 파일의 형식을 변환한다. 변환 전 \texttt{src}와 \texttt{dst} 간의 호환성을 검사하며, 지원하지 않는 변환 요청 시 \texttt{ValueError}를 발생시킨다.

    \texttt{output\_filepath} & \texttt{str} & 지정하지 않을 경우, 원본 파일 경로의 확장자만 변경하여 저장 \\

\subsection{EnergyPlus} \label{subsection:dirstructure-energyplus}
\simulator 에서 EnergyPlus 실행파일 변환 및 실행을 담당하는 idragon 모듈은 2024년 9월 말에 출시된 \texttt{EnergyPlus 24.2}\cite{energyplus242} 버전에 맞추어 개발되었다.

\section{CLI 명령어 명세}
\label{sec:cli_spec}

\texttt{\_\_main\_\_.py}는 사용자의 커맨드라인 입력을 파싱하여 앞서 기술한 API 함수들을 호출하는 진입점이다.

% ---------------------------------------------------------------------------- %
%                                   1. RUN CMD                                 %
% ---------------------------------------------------------------------------- %
\subsection{run: 시뮬레이션 실행}

\begin{codebox}{Syntax}
\texttt{python -m \pymodule{} run [-i INPUT] [-o OUTPUT]}
\end{codebox}

입력 파일의 확장자를 감지하여 적절한 API(\texttt{run\_grexcel} 혹은 \texttt{run\_grjson})를 호출한다.

\begin{itemize}
    \item \textbf{-i, --input}: 입력 모델 파일 경로 (필수)
    \item \textbf{-o, --output}: 결과 파일 저장 경로 (선택)
\end{itemize}

% ---------------------------------------------------------------------------- %
%                                 2. CONVERT CMD                               %
% ---------------------------------------------------------------------------- %
\subsection{convert: 포맷 변환}

\begin{codebox}{Syntax}
\texttt{python -m \pymodule{} convert INPUT [-s SRC] [-d DST] [-o OUTPUT]}
\end{codebox}

\texttt{api.convert} 함수를 래핑(Wrapping)하여 파일 형식을 변환한다.

\begin{itemize}
    \item \textbf{INPUT}: [위치 인자] 변환할 원본 파일 경로
    \item \textbf{-s, --source}: 원본 포맷 (excel, json, idf)
    \item \textbf{-d, --destination}: 대상 포맷 (excel, json, idf)
\end{itemize}

% ---------------------------------------------------------------------------- %
%                                   3. DB CMD                                  %
% ---------------------------------------------------------------------------- %
\subsection{DB: 데이터베이스 인터페이스}

\begin{codebox}{Syntax}
\texttt{python -m \pymodule{} DB DATATYPE [-g KEY]}
\end{codebox}

외부 프로그램(GUI 등)과의 연동을 위해 설계된 명령어로, 조회 결과를 파싱 가능한 JSON 텍스트로 표준 출력(Stdout)한다.

\begin{itemize}
    \item \textbf{DATATYPE}: [위치 인자] 조회할 DB 클래스명 (material, schedule 등)
    \item \textbf{-g, --get}: 조회할 아이템의 Key (구조체는 \texttt{\&}로 연결된 문자열)
\end{itemize}

\begin{codebox}{Output Format (Standard Output)}
\small
명령어 실행 시 아래와 같은 JSON 구조가 출력된다.
\begin{verbatim}
{
    "success": 1,        // 성공(1) 또는 실패(0)
    "result":  {...},    // 요청한 데이터 딕셔너리 (실패 시 None)
    "error":   None      // 에러 메시지 트레이스백 (성공 시 None)
}
\end{verbatim}
\end{codebox}

\section{grjson 구조 (.grm 파일)} \label{section:grm-explanation}

\subsection{규칙}

\subsubsection{변수의 명칭 관련}

\paragraph{사용가능한 문자} 모든 변수의 명칭은 영문 소문자 및 밑줄(\_)로만 구성한다.

\paragraph{복수형과 단수형} 복수 객체 \texttt{array}를 담는 변수의 명칭(예: ``floors") 또는 복수 객체를 담는 하위 분류를 사용하는 변수의 명칭(예: ``profile\_components"), 길는 복수형을 사용하며, 단일 값을 담는 변수의 명칭(예: ``name")은 단수형을 사용한다. 단, 길이가 정해져있거나 각 위치별 의미가 명시적으로 다른 \texttt{array}를 담는 변수의 명칭(예: ``vintage")은 단수형을 사용한다.

\paragraph{축약형의 사용} 모든 변수의 명칭은 축약형을 사용하지 않는 것을 원칙으로 하되, 약어 자체로 통용되는 경우(예: ``cop\_heating")에는 축약형을 사용한다.

\subsubsection{ID 기반 객체 참조 관련} \label{subsubsection:ioref:id_description}
grjson에서 다른 객체의 지칭은 \texttt{ID}값에 기반하여 이루어지며, 모든 객체의 이름(``name")은 사용자 편의를 위한 이름으로 실제 데이터 변환 과정에서 사용되지 않는다.

\paragraph{사용가능한 문자} 모든 ID는 영문 대소문자, 숫자, 하이픈(-), 밑줄(\_)로만 구성되며, 숫자, 하이픈(-) 또는 밑줄(\_)로 시작하지 않는다.

\paragraph{ID의 중복} 동일한 \texttt{ID}는 같은 \texttt{class}의 객체끼리 공유할 수 없다. (모든 \texttt{class}에 대하여 서로 다른 \texttt{ID} 사용을 권장)

모든 변수의 유효성은 필수 및 조건부 사용 여부에 따라 변수(의 속성) 값 존재의 유효성을 검사한 뒤, 타입 및 범위(또는 열거형 상수) 만족 여부를 검사하여 확인할 수 있다.

\paragraph{타입} 모든 변수는 정해진 타입의 변수여야 한다. 모든 변수의 타입은 문자\TypeTag{S}($String$), 실수\TypeTag{F}($Float$), 정수\TypeTag{I}($Integer$), 열거형\TypeTag{E}($Enum$), 불리언\TypeTag{B} 로 구분할 수 있다. 

\paragraph{필수 여부} 입력되지 않을 경우 에러가 발생하는 필수 변수\ReqTag{R}($Required$)와 달리, 비 필수 변수\ReqTag{O}($Optional$)는 미 입력 시 기본값이 사용된다. 단, 입력하지 않았다는 것을 명시적으로 \texttt{null}로 지정해야 하고, 변수 자체를 생락하면 안된다.

\paragraph{조건부 사용 여부} 어떤 변수는 다른 변수(주로 \texttt{type})의 값에 따라 조건부로 사용된다. 이 경우에도 해당 조건에서 필수적으로 요구되는 변수\ReqTag{CR}($Conditional Required$)와 그렇지 않은 변수\ReqTag{CO}($Conditional Optional$)로 구분할 수 있다. 조건에 만족하지 않는 경우, 해당 변수는 json에서 생략될 수 있다.

\paragraph{범위 및 열거형 상수} array면 길이 제약 따짐.
실수\TypeTag{F} 및 정수\TypeTag{I} 타입의 변수는 Python 부동소수점 및 정수 형식에서 표현 가능한 범위 내에서 처리된다.

\section{grresult 구조 (.grr 파일)} \label{section:grr-explanation}
\subsection{class별 명세}
\subsubsection{입력정보 및 계산 방식 관련}
\paragraph{building} 건물 관련 기본 정보를 포함한다.
\begin{itemize}
  \item \textbf{total\_area}: 면적당 지표 계산에 사용되는 건물의 연면적($m^2$)을 의미한다. 연면적의 정의는 \ref{subsec:floorarea_definition_for_EUI}에서 기술한다.
\end{itemize}

\paragraph{constants} 연료별, 용도별, 월별 에너지소요량으로부터, 1차에너지소요량(site2source, $kWh/kWh$), 온실가스 배출량(site2co2, $kgCO_{2,eq}/kWh$) 및 에너지요금(site2cost, $won/kWh$)을 계산하는 데 사용된 변환계수를 포함한다. 각 변환계수의 산출 과정에 대하여는 \ref{subsec:result_converting_coeff_definition}에서 기술한다.

\subsubsection{원시데이터 관련}
에너지소요량을 비롯한 4가지 지표는 용도별 (6가지), 열원별 (4가지), 월별 (12개월)로 제시된다.
\begin{itemize}
  \item 6가지 용도: 난방(heating), 냉방(cooling), 조명(lighting), 팬/펌프/전열교환기(circulation), 급탕(hotwater), 발전(generators)
  \item 5가지 열원: 전기(ELECTRICITY), 천연가스(NATURALGAS), 등유(OIL), 지역난방(DISTRICTHEATING)
\end{itemize}

\paragraph{site\_uses} 건물에서 쓰는거 월별로 원별로 용도별로. 이런식으로 구성되어있음.
\paragraph{source\_uses} 1차에너지에 해당하는 것.
\paragraph{co2} CO2 배출량
\paragraph{cost} 비용. 여기까지 다 site\_uses에다가 곱해서 얻어지는 것임

\subsubsection{요약데이터 관련}
\paragraph{summary\_per\_area} 다 합한 것.
\paragraph{summary\_gross} 에 면적을 곱한 것. 비용 관련된 부분은 얘를 보는 게 맞을 듯.

\subsection{다른 도구와의 관계}
\subsubsection{EnergyPlus(IDFEditor, DesignBuilder, ...)}
이걸 좀 더 사용자 친화적으로 바꾼 개념임. 형상은 이렇게 이해하면 되고 설비는 이렇게 이해해야 함. EP 설비할 때는 이런걸 이렇게 신경썼을텐데 이 툴을 쓸 때는 이런식으로 접근하면 대응되게 할 수 있음.

\subsubsection{ECO2}
입력체계는 거의 비슷하다. 원래 하던대로 하면 된다. 단 형상쪽은 좀 주의해야 할 것임. \par
결과도 비슷한데 환기쪽만 조심하면 됨. ECO2에서 환기는 환기침기부하지만 우리는 그런거 없음. 환기침기부하생기면 냉난방으로 처리하는 거니까 냉난방에 묶여있음. 써큘레이션이라고 팬 펌프 전열교환기만 따로 뽑았음.

>> 이거 레벨 한단계 안올리면 결과파일 관련 내용임
